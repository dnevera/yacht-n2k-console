## 4. Установка «с нуля»

### Stage — работает, но с оговорками
Покрыто: пустой контейнер → bypass onboarding → пользователь `test/test` → HACS из GitHub → интеграция nmea2000 → config entry на `127.0.0.1:4001` (`gateway_type: text`) → карточки → дашборд → HTTP-проверка.

Пробелы:
- Интеграция nmea2000 берётся из `vendor/` (нарушение критерия №3).
- Карточки берутся из `vendor/`, а не из HACS/GitHub-релизов.
- Нет проверки пререквизитов (Python 3, PyYAML, docker CLI, версия compose).
- Нет offline-режима и retry при недоступности GitHub; нет проверки контрольных сумм скачанного.
- `docker compose up -d --force-recreate` (`build_docker.sh:37`) пересоздаёт контейнер каждый запуск.
- `provision_auth()` (стр. 405) не проверяет существование пользователя перед созданием.
- `provision_nmea2000_config_entry()` (стр. 710) не обновляет entry, если host/port изменились.
- Массовые `2>/dev/null` (`deploy.sh:61,65,100`; `deploy_sensors.sh:37,67`) прячут реальные ошибки.

### Prod — сценарий «с нуля» **не покрыт**
`deploy.sh --prod` предполагает, что на хосте уже: Docker, контейнер `homeassistant`, установленный и активированный HACS, установленные через HACS 6 карточек, добавленный custom repository `dnevera/ha-nmea2000` и созданный config entry на tcp-gw.

Отсутствует:
- Скрипта/раздела «Prod prerequisites» с проверкой: SSH без пароля, наличие контейнера, версия HA.
- Автоматической установки HACS на Prod (на Stage автоматизировано, на Prod — только ручной `wget -O - https://get.hacs.xyz | bash -` в `HACS_SETUP.md`).
- Явного порядка шагов «HACS → активация через GitHub device-flow → карточки → интеграция → config entry tcp-gw → `deploy.sh --prod --install`».
- Скрипта отката (бэкапы в `/tmp` создаются, но rollback-команды нет; бэкапы накапливаются без очистки).
- Проверки целостности загруженного перед рестартом HA.

## 6bis. Форки nmea2000 и состояние апстрим-фиксов

Важное уточнение к критерию №3: мы используем **не апстрим, а собственные форки на двух уровнях**. «Убрать копии» здесь означает «тянуть форк из репозитория по пину», а не «перейти на апстрим».

**Целевая модель доставки (утверждена 2026-08-10): никаких патчей поверх PyPI — только установка из наших форков по пину**, одинаково для контейнера HA и для нашего venv/Docker. Патч-скрипты после перехода удаляются полностью, а не «до выхода релиза апстрима».

### 6bis.1 Два уровня форка

| Уровень | Апстрим | Наш форк | Как доставляется сейчас |
|---|---|---|---|
| Python-библиотека `nmea2000` (декодер) | `tomer-w/nmea2000` | `dnevera/nmea2000`, тег **`cpu-overload-fix`** (коммит `6c9df918d19a`) | Сейчас: PyPI `nmea2000==2026.5.2` (`requirements.txt:43`) + патчи `patches/nmea2000_ioclient.py` и `scripts/patch_ha_nmea2000_message.py` через корневой `deploy.sh --patch-ha`. **Должно стать:** `nmea2000 @ git+https://github.com/dnevera/nmea2000.git@cpu-overload-fix` |
| HA-интеграция `ha-nmea2000` | `tomer-w/ha-nmea2000` | `dnevera/ha-nmea2000`, тег **`ydnu-02-usb-tcp-gw`** (коммит `2cdef78c6df2`) | Сейчас: zip ветки `bumblebee-custom` в `.cache/` (или `vendor/`); Prod: HACS custom repository. **Должно стать:** zip/HACS по тегу |

В `manifest.json` нашей интеграции requirement указан как `git+https://github.com/dnevera/nmea2000.git@fix/pgn-126996-hash-collision-per-source#egg=nmea2000`, то есть интеграция тянет форк библиотеки внутрь контейнера HA. Это **второй, независимый канал доставки** — его нельзя смешивать с «PyPI + патчи», иначе версия библиотеки в контейнере становится недетерминированной.

### 6bis.2 Теги форков (проверено 2026-08-10)

**`dnevera/nmea2000` → тег `cpu-overload-fix`** (`6c9df918d19a`, = HEAD ветки `fix/pgn-126996-hash-collision-per-source`). Содержит **оба** фикса:
- Bug 1 (EOF spin-loop): `nmea2000/ioclient.py:537` — `raise ConnectionError("Connection closed by remote host")` (плюс стр. 943 в BDTP-клиенте).
- Bug 2 (коллизия PGN 126996): `nmea2000/message.py:225–236` — `source_id` из `self.source_iso_name.unique_number`, `primary_key = f"{self.id}_{source_id}"`.

Следствия:
- Ветка `fix/text-gateway-eof-spin-loop` (`b8218810`) больше не нужна как отдельный источник.
- `pyproject.toml:7` → `version = "2026.5.2"` совпадает с PyPI-версией апстрима: установленный из форка пакет неотличим по `__version__`, drift-guard по версии работать не будет. Нужен бамп (например `2026.5.2+ydnu.1`).
- GitHub Releases нет, только теги — для `git+`-установки достаточно. `cpu-overload-fix` — lightweight-тег без семантики версии; желателен семантический тег (`v2026.5.2-ydnu.1`) + хранение sha `6c9df918d19a` в манифесте.

**`dnevera/ha-nmea2000` → тег `ydnu-02-usb-tcp-gw`** (`2cdef78c6df2`, = HEAD ветки `bumblebee-custom`), `manifest.json`: `"version": "2026.5.0-fix1"`.

⚠️ **Незакрытый хвост:** в `manifest.json` на этом теге requirement всё ещё указывает на **ветку** библиотеки:
```json
"requirements": ["git+https://github.com/dnevera/nmea2000.git@fix/pgn-126996-hash-collision-per-source#egg=nmea2000"]
```
Пока это не заменено на `@cpu-overload-fix` и не перетегировано, установка «с нуля» остаётся невоспроизводимой. Правка на стороне форка интеграции.

### 6bis.2a Состояние фиксов в апстриме (проверено 2026-08-10)

**Bug 1 — EOF spin-loop в `TextNmea2000Gateway`: влит в апстрим, но не в релизе.**
- PR `tomer-w/nmea2000#61` — `state=closed`, `merged=true`, `merged_at=2026-07-30T21:51:10Z`, база `main`.
