# AIS Dashboard (`ha/ais/`)

Home Assistant dashboard package that plots live AIS (Automatic
Identification System) targets — other vessels' position, course, speed and
identity data — on the same map as the boat's own GPS position, alongside a
full, clickable target table (MMSI, name, callsign, type, size, destination,
SOG/COG/heading/nav status) for every currently-tracked vessel.

Sibling package to [`ha/sailing-dash/`](../sailing-dash/README.md), built and
deployed the same way (own `config.yaml`/`.env`, `helpers/build.py` compiling
`src/yaml/**` into `build/`, an idempotent `deploy.sh`), but deliberately
self-contained: it does not read `ha/sailing-dash/.env` or share any live
state with it.

## How it works (gateway-direct, NOT via the nmea2000 HA integration)

AIS is deliberately **not** decoded by the `nmea2000` HA integration: doing so
would create a throwaway device + `sensor.ais_*` batch per passing MMSI and
flood HA's registry/recorder DB in busy waters. Instead:

1. The custom `ais_targets` HA integration
   ([`custom_components/ais_targets/`](custom_components/ais_targets/README.md))
   opens a TCP socket to the **YDNU-02 gateway** (`gw_host:gw_port`, default
   port 4001), reads the raw N2K stream, decodes the AIS PGNs
   (129038/129039/129040 position; 129794/129809/129810 static & voyage) in
   RAM, and keeps a per-MMSI target table — nothing hits the HA registry
   except the live `geo_location.ais_<mmsi>` entities.
2. `01_ais_map.yaml` plots `device_tracker.nevera` (own GPS position,
   unchanged) together with `geo_location_sources: ['ais_targets']` on a stock
   `type: map` card sized to the FULL dashboard width with a fixed height (not
   a full-screen panel).
3. A `custom:auto-entities` + `custom:flex-table-card` table lists every live
   `geo_location.ais_*` target with all fields; each row is clickable and
   opens that vessel's more-info dialog with its mini-map.
4. Your own boat can appear as a normal AIS target too: set `own_mmsi` on the
   integration (the single source of truth) — that target is named
   "Bumblebee", listed in the table, and given a distinct source so it is
   never plotted twice next to `device_tracker.nevera`.
5. Targets that stop reporting for longer than the stale timeout (default 10
   minutes) are removed automatically.

## Dependency: the `nmea2000` library (not the HA integration's AIS decoding)

The `nmea2000` **library** must be importable inside HA (declared in the
integration's `manifest.json`; already present because `ha/sailing-dash` uses
the `nmea2000` HA integration for its wind/depth/etc. sensors).

`./deploy.sh --install` here does the OPPOSITE of adding AIS to that
integration: it **removes** the AIS PGNs from its `pgn_include` and sets
`exclude_AIS = True` (`helpers/patch_pgn_include.py`), so the integration
never decodes AIS and never pollutes the registry. AIS is owned entirely by
`ais_targets`.

## Layout

```
ha/ais/
├── .env.template                 # target profiles (stage/prod)
├── config.yaml.template          # deployment-level options only (optional)
├── deploy.sh                     # --install / --update / --dashboard-only
├── custom_components/
│   └── ais_targets/               # gateway-direct AIS → geo_location integration
│       ├── ais_bus.py             # TCP gateway reader + in-memory AIS decoder
│       ├── geo_location.py        # dynamic geo_location.ais_<mmsi> entities
│       ├── config_flow.py         # gw_host/gw_port/own_mmsi/intervals
│       └── const.py / __init__.py / manifest.json
├── helpers/
│   ├── build.py                   # concatenates src/yaml/** -> build/dashboard-ais.yaml
│   ├── deploy_dashboard.sh        # idempotent upload into .storage/lovelace.dashboard_ais
│   ├── patch_pgn_include.py       # idempotently KEEP AIS out of the nmea2000 entry
│   ├── verify_ais_targets.py      # drift-guard: AIS PGNs decodable by nmea2000/pgns.py?
│   └── lib/                       # ha_target.sh / env_profile.sh — thin copies of sailing-dash's
├── src/yaml/dashboard/            # SINGLE SOURCE OF TRUTH for the whole view
│   ├── header.yaml                # panel view (edge-to-edge)
│   └── sections/
│       └── 01_ais_map.yaml        # map + overlay target table: styles, sizes, columns
└── build/                         # generated by build.py, gitignored
```

## Usage

```bash
cp .env.template .env                 # edit stage/prod host + container names

# Map size/zoom, overlay geometry and table columns are edited DIRECTLY in
# src/yaml/dashboard/** — build.py only concatenates those files and never
# rewrites anything inside a card, so hand edits always survive a deploy.

# First-time install:
./deploy.sh --stage --install
./deploy.sh --prod  --install

# Refresh only the dashboard after editing src/yaml/dashboard/**:
./deploy.sh --stage --update
```

`--install` additionally: copies `custom_components/ais_targets` into the
target's HA config (idempotent, sha256-diff copy), cleans AIS out of the
`nmea2000` config entry, and fetches + registers the `auto-entities` +
`flex-table-card` Lovelace resources the target table needs.

**After installing**, configure the integration once via the HA UI
(Settings → Devices & services → Add integration → "AIS Targets") and set at
least `gw_host` (the gateway host as reachable from HA) and your `own_mmsi`.

## ⚠️ Verify against live traffic on first real deploy

This package was developed with no live AIS targets on the bus at build time
(none were nearby). The field ids / units were taken directly from the
installed `nmea2000` fork's `pgns.py` and covered by unit tests
(`tests/test_ais_targets_bus.py`), and the same field ids were confirmed on
real targets in an earlier live-bus discovery session — but do sanity-check
the first real deployment: confirm targets appear on the map, the table shows
all columns, clicking a row centers/opens the vessel, and stale targets drop
after the timeout.
