# AIS Dashboard (`ha/ais/`)

Home Assistant dashboard package that plots live AIS (Automatic
Identification System) targets — other vessels' position, course, speed and
identity data — on the same map as the boat's own GPS position, alongside a
detail list (MMSI, name, callsign, type, size, destination) for every
currently-tracked vessel.

Sibling package to [`ha/sailing-dash/`](../sailing-dash/README.md), built and
deployed the same way (own `config.yaml`/`.env`, `helpers/build.py` compiling
`src/yaml/**` into `build/`, an idempotent `deploy.sh`), but deliberately
self-contained: it does not read `ha/sailing-dash/.env` or share any live
state with it beyond the same underlying `nmea2000` bus data.

## How it works

1. An AIS receiver/transceiver already wired to the NMEA 2000 bus reports
   other vessels' data as PGNs 129038/129039/129040 (position reports),
   129041 (Aid to Navigation), 129793 (UTC/date), 129794 (Class A static &
   voyage data) and 129809/129810 (Class B static data, message 24 parts A/B)
   — all already decodable by this project's `nmea2000` fork (see
   `.agents/skills/nmea2000-setup/SKILL.md`), confirmed locally by
   `helpers/verify_ais_targets.py` against the installed package.
2. The custom `ais_targets` HA integration
   ([`custom_components/ais_targets/`](custom_components/ais_targets/README.md))
   scans the raw per-field `nmea2000` entities the `nmea2000` HA integration
   already creates for those PGNs, groups them by MMSI, and creates/updates
   one `geo_location.ais_<mmsi>` entity per vessel — the idiomatic HA
   mechanism for an unbounded, changing set of map objects (same approach as
   the built-in `adsb`/`opensky` integrations).
3. The dashboard's `01_ais_map.yaml` section plots `device_tracker.nevera`
   (the boat's own position, unchanged) together with
   `geo_location_sources: ['ais_targets']` on a stock `type: map` card, plus
   a native `type: markdown` card listing MMSI/name/callsign/type/length/
   beam/destination for every live target.
4. Targets that stop reporting for longer than the configured stale timeout
   (default 10 minutes) are automatically removed by the integration.

## Dependency: the `nmea2000` HA integration + its `pgn_include` allow-list

This package assumes the `nmea2000` HA integration is **already installed
and configured** — that bootstrap lives entirely in `ha/sailing-dash/`
(`deploy.sh --bootstrap`/`--install`), not here.

`pgn_include` on that integration's config entry is a **silent allow-list**:
a PGN missing from it produces no error, the corresponding entities simply
never appear (a failure mode already documented for this project — see the
nmea2000-setup skill). `./deploy.sh --install` in this package verifies and,
if needed, patches that allow-list (`.storage/core.config_entries`) to add
the AIS PGN set: `129038, 129039, 129040, 129041, 129793, 129794, 129809,
129810` — via `helpers/patch_pgn_include.py`, an idempotent JSON patch (safe
to re-run; only appends what's actually missing).

## Layout

```
ha/ais/
├── .env.template                 # target profiles (stage/prod), see ha/sailing-dash's for the same mechanism
├── config.yaml.template          # map zoom/aspect, stale timeout, detail-list fields
├── deploy.sh                     # --install / --update / --dashboard-only
├── custom_components/
│   └── ais_targets/               # the geo_location bridge integration (see its own README.md)
├── helpers/
│   ├── build.py                   # compiles src/yaml/** -> build/dashboard-ais.yaml
│   ├── deploy_dashboard.sh        # idempotent upload into .storage/lovelace.dashboard_ais
│   ├── patch_pgn_include.py       # idempotent pgn_include JSON patch
│   ├── verify_ais_targets.py      # drift-guard: AIS PGNs present in nmea2000/pgns.py?
│   └── lib/                       # ha_target.sh / env_profile.sh — thin, documented copies
│       └── ...                    # of ha/sailing-dash's shared shell access layer
├── src/yaml/dashboard/
│   ├── header.yaml
│   └── sections/
│       └── 01_ais_map.yaml        # map card + geo_location_sources + detail list card
└── build/                         # generated by build.py, gitignored
```

## Usage

```bash
cp .env.template .env          # edit stage/prod host + container names
cp config.yaml.template config.yaml   # optional: tweak map zoom, stale timeout, detail fields

# First-time install on a target that already has the nmea2000 integration
# configured (from ha/sailing-dash's bootstrap):
./deploy.sh --stage --install
./deploy.sh --prod  --install

# Refresh only the dashboard after editing src/yaml/dashboard/**:
./deploy.sh --stage --update
./deploy.sh --stage --dashboard-only   # same as --update
```

`--install` additionally copies `custom_components/ais_targets` into the
target's HA config directory (idempotent, sha256-diff directory copy) and
patches `pgn_include` as described above; `--update`/`--dashboard-only` only
touch the Lovelace dashboard.

## ⚠️ Known limitation of this implementation

This package was developed entirely in a sandboxed environment with **no
network access to a live NMEA 2000 bus, a running Home Assistant instance,
or `bumblebee.local`** — every piece of the deploy tooling (idempotent
sha256-diff delivery, `.storage` merge, `pgn_include` patch, drift-guard) was
verified against local fixtures/synthetic data and the locally-installed
`nmea2000` fork only, never against real traffic or a real HA container.

The one piece that could **not** be verified at all is the exact entity_id /
attribute shape the `nmea2000` HA integration produces for AIS PGNs — see
[`custom_components/ais_targets/README.md`](custom_components/ais_targets/README.md)
for the full reasoning, the defensive matching strategy used, and exactly
what to re-check once this is deployed against a live AIS receiver.
