# What a FRESH Home Assistant install needs before the Sailing dashboard
# (dashboard-sailing.yaml + sensors-sailing.yaml) can be deployed to it.
#
# This is NOT a pip requirements file for Home Assistant itself — HA core
# ships everything the dashboard needs (rest:, template:, device_tracker:,
# map/gauge/tile/entity/heading cards, sensor & config machinery) out of the
# box. What's listed below is the extra, non-default setup: тыS + three
# HACS-installed frontend custom cards, plus the deploy tooling requirements
# already covered in the repo root requirements.txt.
#
# See ha/sailing-dash/README.md ("Setting this up from scratch on a new HA
# instance") for the exact deploy order/commands.

# ── 0. NMEA 2000 integration (domain "nmea2000") — THE ACTUAL DATA SOURCE ───
# https://github.com/dnevera/ha-nmea2000 (our own fork, branch
# "bumblebee-custom", of upstream tomer-w/ha-nmea2000) — installed via HACS
# (custom repository) on Prod (bumblebee.local), NOT one of the 3 frontend
# cards in section 2 below. This is the integration that connects to
# ydnu02_tcp_gateway (or, on Stage, local-ha/mock_nmea_emulator.py) on :4001
# and creates ALL N2K-derived sensor entities (COG/SOG, wind angle/speed,
# STW, depth, GPS lat/lon) this dashboard depends on — without it,
# dashboard-sailing.yaml renders with a fully provisioned Lovelace/cards but
# every N2K entity is "unavailable"/empty.
# For a LONG TIME this was missing from Stage entirely: no HACS, no
# /config/custom_components/nmea2000, no config entry — `stage_provisioner.py`
# only ever provisioned the dashboard/cards/auth, never the data source itself.
# Fixed: `stage_provisioner.py`'s `deploy_nmea2000_integration()` +
# `provision_nmea2000_config_entry()` now install a vendored copy of the
# integration (`ha/sailing-dash/vendor/custom_components/nmea2000/`, mirrored
# from OUR OWN fork above, whose manifest.json is already patched to require
# our own `dnevera/nmea2000` library fork — HACS is just a downloader, copying
# the same files has the same runtime effect) and auto-register a
# `gateway_type: text` config entry pointed at `127.0.0.1:4001` (local-ha
# uses `network_mode: host`, so it reaches `mock_nmea_emulator.py` directly).
# HA then installs the manifest's own pip requirement automatically on first
# load — pinned in our vendored `manifest.json` to the SAME patched git fork
# as this project's own `requirements.txt`
# (`dnevera/nmea2000@fix/pgn-126996-hash-collision-per-source`), so Bug 1/
# Bug 2 from the nmea2000-setup skill are already fixed, no separate
# `--patch-ha` step needed on Stage.
# On Prod, this is still installed for real through HACS (Settings -> HACS ->
# Integrations -> Custom repositories -> add `dnevera/ha-nmea2000`) pointed
# at the real gateway's host:4001 — the vendored copy here is Stage-only
# tooling.
#
# ── 1. HACS (Home Assistant Community Store) ────────────────────────────────
# Required on PROD to install the NMEA 2000 integration above (as a custom
# repository, since it's our own fork, not in the default HACS store) and
# the custom Lovelace cards below through the UI. Not a pip package —
# install via the official HACS installer:
# https://hacs.xyz/docs/use/download/download/
# then add HACS through Settings -> Devices & Services -> Add Integration.
# Also installed for real on Stage (`local-ha`) since 2026-08-10:
# `stage_provisioner.py`'s `deploy_hacs_integration()` downloads the SAME
# official HACS release used on Prod (github.com/hacs/integration, cached
# under `ha/sailing-dash/.cache/hacs/`, gitignored — not vendored/committed,
# it's a ~50MB prebuilt frontend bundle) into `/config/custom_components/hacs/`,
# so Stage genuinely has HACS installed, not just a copy-only emulation of
# what it would do. The one manual step that can't be automated headlessly is
# completing HACS's GitHub device-flow login once in the HA UI (Settings ->
# Devices & Services -> HACS) to activate it, same as on a fresh Prod install
# — after that you can add `dnevera/ha-nmea2000` as a custom repository
# through the real HACS UI instead of relying on the vendored
# `deploy_nmea2000_integration()` copy below. If the container has no
# internet access during provisioning, HACS install is skipped with a
# warning and the vendored nmea2000/card install below still runs regardless
# (it never depended on HACS being present).

# ── 2. HACS Frontend custom cards (Settings -> HACS -> Frontend) ────────────
# Install these three, in this order (card-mod is a soft dependency others
# rely on for styling tricks used on this dashboard):
#   1. card-mod        https://github.com/thomasloven/lovelace-card-mod
#                       (used by the glance header value styling; the Windy
#                       widget no longer needs it — see 2d)
#   2. compass-card    https://github.com/tomvanswam/compass-card
#                       (used by the Wind/COG compass tiles)
#   3. apexcharts-card https://github.com/RomRider/apexcharts-card
#                       (used by the Wind History & Forecast chart)
# See lovelace-resources.yaml for the exact resource URLs already registered
# on the reference instance (bumblebee.local) — for documentation only, HACS
# registers its own on install, do not copy those URLs/ids verbatim.
#
# ── 2b. windrose-card — NOT via HACS, manual install (2026-08-09) ───────────
# https://github.com/aukedejong/lovelace-windrose-card (v2.4.2 used here) —
# renders the "Wind Direction — History (rose)" card as a real polar
# windrose from recorder history. This one was NOT installed through HACS
# (it isn't in the 3-card list above): the release .js was downloaded
# directly and copied to config/www/windrose-card.js, then registered as a
# Lovelace resource (/local/windrose-card.js, type: module) via
# .storage/lovelace_resources — same end result as a HACS "Manual install",
# see the card's own README for that path, or install it via HACS instead
# if it has since been added to the default store.

# ── 2c. config-template-card — NOT via HACS, manual install (2026-08-09) ───
# https://github.com/iantrich/config-template-card (v1.3.6 used here) —
# lets a card's config be templated with plain JS `${...}` (evaluated by the
# card itself, NOT Jinja). It used to wrap the Windy iframe; that is gone as
# of the windy-boat-card rework (see 2d), so this card is currently kept
# registered but unused — safe to skip on a fresh install unless something
# starts using it again. Installed the same way as windrose-card/
# plotly-graph-card: release .js copied to config/www/config-template-card.js,
# registered as a Lovelace resource (/local/config-template-card.js).

# ── 2d. windy-boat-card — OUR OWN card, source in this repo (2026-08-09) ────
# ha/sailing-dash/src/js/cards/windy-boat-card.js — the Windy embed widget plus a
# working "center on the boat" button. It exists because the embed's built-in
# postMessage API (enabled by `embedMake=true` in the embed URL) is the only
# way to re-centre the map without reloading the iframe, and HA's built-in
# `type: iframe` card cannot send that message. Nothing to download: the file
# is committed here and `./deploy.sh --resources-only` uploads it to
# config/www/windy-boat-card.js and registers /local/windy-boat-card.js.

# ── 3. HA core integrations used (already bundled, nothing to install) ──────
# - rest:      (sensor.wind_forecast_rest — polls api.open-meteo.com)
# - template:  (sensor.wind_forecast_flat, sensor.barometer_mmhg,
#                sensor.boat_latitude/boat_longitude, device_tracker.nevera)
# - map / gauge / tile / entity / heading / iframe / button / grid / sections
#   Lovelace card & view types
# NOTE: the native "Open-Meteo" HA integration (config-flow based) was
# evaluated and is explicitly NOT used here — its hourly forecast lacks
# wind_speed/wind_gust, see README.md "Forecast location follows the boat's
# GPS" for details. Do not install/enable it for this dashboard.

# ── 4. Tooling on the machine running the deploy scripts (NOT on HA) ────────
# Already covered by the repo root requirements.txt:
#   pyyaml>=6.0       (deploy_dashboard.sh / deploy_sensors.sh YAML <-> JSON)
#   websockets>=12.0  (optional, only for verifying live lovelace/config)
# Plus SSH + passwordless sudo on the HA host for docker exec/cp/restart
# (same as deploy.sh:patch_ha(), see repo root README/TECHNICAL.md).

# ── 5. Entities this dashboard assumes exist already ────────────────────────
# All N2K-derived sensors (COG/SOG, wind angle/speed, STW, depth, GPS
# lat/lon) are published by ydnu02_tcp_gateway — see the nmea2000-setup
# skill / repo root AGENTS.md for how those get into HA. This dashboard does
# not work standalone without that gateway already running and publishing.
